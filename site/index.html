A control plane, and the course that builds it

Cybernetic control
for agentic software.

VSM-Pi asks whether Stafford Beer's Viable System Model can run inside an autonomous coding agent — not as five chatbot personas, but as explicit functions, authority boundaries, typed channels, verification gates, and feedback loops. It ships its own orchestrator to find out, and a course, Viable Agents, that builds it lesson by lesson.

Product

VSM-Pi

A coding-agent harness built on Pi, with a typed VSM control plane layered on top of it — designed against one recurring failure mode of autonomous agents: architectural drift that outruns anyone's ability to review it.

Design goals

  • Keep the orchestrator small — the S3 loop of contract → dispatch → verify → route → close, generic over workloads.
  • Declare the control plane rather than assemble it: registry, capability profiles, policy, and workload live in a versioned, checked definition.
  • Make S5 identity and policy durable and version-controlled, independent of any one context window.
  • Keep S3* audit independent of S1 self-reporting.
  • Differentiate operations by capability profile, not roleplay persona.

Control model

Six functions, one loop

Beer's Viable System Model, read as a harness architecture. Regulatory variety flows down as attenuated instruction and back up as amplified evidence — S3* audits independently of what S1 reports, and S4 argues with S3 about the future on S5's terms.

S1 units act directly on the environment; S3* audits independently of what they report; S4 and S3 argue about now vs. next, arbitrated by S5 policy.
Mechanism hierarchy

Prefer the mechanism that survives adversarial pressure

When adding a feature to the harness, VSM-Pi walks this ladder from the top down. It is an ordering by reliability, not by elegance: if you can write the check, don't write the paragraph.

1
TypeScript invariant
Use the type system — errors that can't compile.
2
Deterministic runtime check
A gate that mechanically enforces a rule at execution time.
3
Structured tool / protocol
A runtime schema and a typed message, not a free-text instruction.
4
Model judgment
Reached for when the decision genuinely requires interpretation.
5
Prompt / context engineering
Advice for what no gate above it can know — taste, intent, convention.

Architecture

VSM-Pi provides its own orchestrator

The project does not scope itself as a regulation layer riding on GSD-Pi's workflow kernel. GSD-Pi is mid-cutover to a database-authoritative lifecycle, OpenGSD is fanning out into separate projects, and the course lab already proved the regulation layer needs an orchestrator, not GSD's — ten checkpoints of gates, effects, profiles, leases, contracts, budgets, recovery, audit and authority run on bare Pi. packages/ has no GSD dependency; GSD-Pi stays in the course purely as comparison material. How a unit runs through the loop is drawn out on its own page.

The orchestrator, sized

Nothing but the S3 loop, generic over workloads, with leases, budgets, and attempts as immutable records. All five stages exist in course/lab/src/controller.ts:

contract → dispatch → verify → route → close

What made GSD heavy — seven fixed phases, milestone lifecycles, UAT, projections — is workload, and lives in a workload definition, not in this loop. Recovery decisions cite a versioned policy; closeout is refused on anything but fresh, host-run evidence.

The first workload: the autoloop

The software-development autoloop is the first workload definition, and the one the course builds against its fixture repository — "build my own GSD" satisfied by declaring one rather than adapting it:

plan implement verify integrate close

five unit types, declared in workload/software-development.json, each naming:

A capability profile the unit runs under — implement may write src/ and test/; research is read-only by declared effect
Checks the orchestrator re-runs itself at closeout — run_checks, run_tests — bound to the revision they ran against
Still design: S4 triggers that raise a unit unasked (lesson 11) and consent before irreversible actions (lesson 13)
Status

The loop runs; the metasystem is next

The S3 loop exists end to end — contract, dispatch, verify, route, close — with leases, budgets, a versioned recovery policy, a closeout gate over host-run evidence, and protected identity. Lessons 11–15 add environmental intelligence, obligations, the complete identity set, the algedonic channel, evals and packaging. course/lab is the reference build; each checkpoint promotes into packages/ as it stabilizes. The course

Viable Agents — build your own coding-agent harness

Most agent courses teach you the buttons. This one teaches the control system, and you leave holding a harness you wrote yourself: regulator, which is VSM-Pi's reference build. Each module opens with a regulatory question an autonomous coding agent forces on you, derives the mechanism that answers it, then shows the Pi feature, the GSD-Pi production comparison, and the typed VSM-Pi treatment.

Who it's for

Senior / staff engineers
running agents on real codebases — a principled reason for every guardrail, tuned to their repo.
Platform & DevEx teams
a design method for an internal agent platform, plus the evaluation machinery to prove it helps.
Agent-tool builders
deep Pi extension/SDK competence and a structural critique of "five agents in a trench coat."
Technical leaders
a vocabulary for where autonomy is safe, and what evidence would demonstrate it.

By the end, a participant can

  1. Describe a coding-agent harness as a control system: what regulates what, over which channel, with what authority, closing which feedback loop.
  2. Apply the mechanism hierarchy instead of solving every problem with prompt text.
  3. Extend Pi confidently — typed tools, the tool-call lifecycle, context shaping, per-phase model routing, SDK/RPC, packaging.
  4. Design work units as contracts — fixed, delegated, unresolved — rather than prose task descriptions.
  5. Build audit that does not depend on the executor's self-report.
  6. Keep system identity durable and version-controlled instead of trapped in a context window.
  7. Decide when a human must be interrupted, and build the channel that does it.
  8. Measure whether their regulation actually improved outcomes, with a control arm.
