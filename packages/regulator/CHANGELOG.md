[Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions follow

- Workload-declared tools, and consent derived from a declared effect (#121, under #61). A workload may declare tools of its own under `tools[]` in `workload/<name>.json` (`DeclaredToolSchema` in protocol): a name, the description and the parameters schema the model sees, an `effect` in the shape every built-in declares (`ToolEffectSchema`), and a `program` in the command runner's shape (`ProgramSchema`: argv under the definition, `outputs` as its whole reach, an optional timeout). The Pi host's new `declared-tools` extension registers every declared tool generically from the definition at load, knowing nothing of what it does; the profile grant puts one on the surface by name, as for a built-in, and `readOnlyViolations`, `isReadOnlyProfile` and `effectOf` read the declared effects beside the built-in table, so a read-only profile cannot be granted an irreversible declared tool. A call runs the program in the unit's worktree through the control plane's own runner (`runDeclaredTool`, over the `runProgram` the command dispatcher now shares; the process runner takes `input` for stdin) with the call's arguments on stdin as JSON: a write outside the declared outputs is undone and the call refused, a non-zero exit or a timeout is refused with what the program said, the last stdout line is what the model is told, and the program's file, hash, exit and writes are a `regulator:declared-tool` session entry. One thing is derived from the declaration, the only thing the control plane derives from an effect: a declared tool whose `sideEffects` is `irreversible` needs a person's recorded yes for the call before it runs. `consentRequiredFor` (core) reads the declared effects beside the profile's `consent[]` and derives a bare grant on every call of such a tool with no profile naming it; the host's interception and the lab's `consentGate` both read it, the refusal is the same operational-signal naming the derivation, the record matches the call's arguments as a grant's does, so `answer --amend` and a yes held across attempts work unchanged. The derivation stops at workload-declared tools: `ask_human` and `notify_owner` are irreversible and are the channels to a person. `regulator check` refuses a declared tool with a built-in's or another workload's name, a schema that is not an object's, an effect that says arbitrary execution or disagrees with its outputs, a program naming no file under the definition or an output outside the project or under a harness-owned prefix, and a profile that grants an irreversible declared tool beside a plain `write` or `edit` under its outputs (a write there would need no yes); a shell beside it is warned about as the sandbox bypass is. `regulator doctor` gains `manifest-writable`: an instance manifest whose writable prefixes reach a declared tool's guarded outputs is refused, naming the line to drop. `ENFORCEMENT_POINTS.tool` gains `declared`, the one point every declared tool's execute stands under. The portfolio is the case: `place_trade` (`workload/portfolio/place-trade.mjs`) takes `{ proposed }` and writes `trades/pending/<date>.json` byte for byte from the proposed list; the `manager` profile grants it by name, lists no consent grant and no longer writes under `trades/pending/` at all; the advice line that said to ask before writing a trade list is deleted; `confirm-trades` asks once naming the call and places the list with the tool; the scripted `careless` unit calls the tool without asking and is refused before the file exists, and its old shortcut — a trimmed list after the yes — is impossible by construction, so the fixture's pending-equals-proposed assertion now guards a bug in the tool. - The `command` runner (#122): a unit type declares how it runs. `unitTypes[].runner` is `{ "kind": "session" }`, the default when absent, or `{ "kind": "command", "argv", "timeoutMs"?, "outputs" }`: a program the control plane runs itself in the unit's worktree through the same `Dispatcher` seam and the same steps as a session — start, lease, worktree, dispatch, report, route, close — with no host and no model, with the contract path and the attempt in its environment, under the policy's `wallClockMs` for the unit type as its one budget (tokens, cost and turns zero by construction), its file resolved under the definition as a grader's is and hashed into the attempt record with its exit (`AttemptRecord.program`). - The accept-path split, slice 2 (#138): the prediction record, its resolution from the stores, and the typed `harness-edit` payload. An intelligence signal may carry a `prediction` block — the metric it stakes (built-in or declared), a baseline (a committed report's arm, by the SHA-256 of the report's file), a direction and a size, a `probability` in [0, 1] beside the three-valued `confidence`, and `horizons[]`, each `probe` (a report by fingerprint and an arm) or `live` (the next N units of named types) with the grader value that counts against it. A signal without the block is unchanged and routes as it did; a block missing a part, a probability outside [0, 1] or an unknown metric is refused by the schema. `prediction-resolution` is a new line of the regulatory log, three-valued: at a unit's close or abort the loop reads the named metric with the eval harness's graders over the stores (never the unit's report), compares it with the baseline and the disconfirming value, and appends one reading per unit; a probe horizon resolves once from the committed report it names, against the arm's interval. Disconfirmed is read first; confirmed needs the baseline moved by the magnitude; everything else is inconclusive, which counts against the prediction's precision and never for the edit. A disconfirmed live horizon is a proposal from S3 to S5 to revert or re-decide the advice, routed under the routing policy into an obligation with the prediction's id in its subject; no file is reverted. `HarnessEditSchema` types a proposal's `requestedChange` as a diagnosis (references to evidence records and signals with the unit, attempt, revision and trajectory moment), a change (the diff against one advice file, by profile) and the prediction's id; a payload that claims the kind and lacks a part is refused by the schema, a plain proposal is unaffected. `advice accept` reads a `harness-edit` against the stores first (`checkHarnessEdit`: every diagnosis reference resolves, the prediction carries the block, the profile is declared), takes the target from the payload (`--file`, if given, must agree), cites the prediction's id in the disposition, and the live horizon is open from that decision, read from the obligation; a plain proposal is decided as before. `regulator status` lists every prediction with its horizons, what bet on it, each reading and a precision that counts inconclusive against. The record is `prediction-resolution` (50 records, 48 active); `BOUNDARY.md`'s advice row names the payload. The probe rule and the probe arm are slice 3, after #46; nothing produces a prediction yet.

A suite pre-registers a declared name as it does a built-in one and may mark one declared metric `optimise`, the one an optimiser could select on; everything else is reported only, and nothing optimises anything. `regulator check` refuses a suite naming a metric no workload declares, a workload naming a metric it does not own or twice, a grader whose command names no file under the definition, a second optimisation target or a built-in as one, and a judged metric (an instrument ref) until the instrument record carries its held-out score — which no record does yet. `runSuite` runs each declared grader after every unit, in the instance, reading `{ metric, value, observation? }` per line and refusing a grader that fails, measures what it was not declared for or emits nothing for what it was; the values are summarized and lifted exactly as the built-ins, and the report's fingerprint carries each grader's command and file hash. ## [0.1.3] — 2026-09-29

The second live drift run (issue #46, on 0.1.2) closed ten of twelve units and found
what happens after the budget guard halts one.

### Fixed
- A halt by the budget guard was failed over as a provider failure. The guard aborts the session when a ceiling is crossed and Pi records the abort as an errored assistant message; the dispatcher read the message alone, opened a fresh session on each declared fallback, and reported "every model in the route failed" when the last one did. Each fallback session also started a new ledger for the same attempt, so the primary's spend and the exhausted marker were overwritten and the loop classed the unit as a dispatch error (recovery cause `environment`) instead of `budget-exhausted`, which the recovery policy routes differently. The dispatcher now reads the attempt's ledger before deciding (`attemptEnd`): a halt is returned to the loop as the attempt's end and is never failed over; only an errored message without a halt is a provider failure. A session that opens on an attempt another session already metered resumes that ledger (`BudgetMeter` `resume`), so the attempt has one ledger whichever sessions ran it, the primary's spend counts against the same ceiling, and a halt stays a halt.
- The default policy's last fallback for every route, `google/gemini-2.5-flash`, is retired by Google for new keys and answered every call with a 404; the routes now fall back to `google/gemini-3.8-flash`, which the pinned Pi registry knows. Nothing checks a route against the provider before dispatch; the `model-router` card says so.
- `regulator unit show … | head` crashed the CLI with `EPIPE` once the reader closed the pipe; the CLI now exits cleanly.

### Migration

The floor the migration notes count from, written retroactively with #53. Nothing an instance carries changed between 0.1.0 and 0.1.3: `init` seeded `regulator/identity/` and added the `.regulator/` ignore line under each, and the identity seed is byte-identical across the four (the policy, profile and registry changes of 0.1.1 to 0.1.3 are read from the definition). A manifest without `definition.packageVersion` was written by one of these four and is read as 0.1.3 by `regulator upgrade`.

## [0.1.2] — 2026-09-28

The first live drift run (issue #46) found the live dispatch path had never been
exercised end to end.

### Fixed
- Live units ran with every session-bound regulator inert. The dispatcher created a Pi session and prompted it, but never called `session.bindExtensions(...)`, which is what emits `session_start` in Pi's own modes. The contract, the profile grant, the budget guard, the identity section and the algedonic path all initialize on that event, so a live unit ran as a plain coding agent: no contract in its prompt, `report_result` refused for want of a contract, nothing metered, every unit blocked as `no-report`. `openUnitSession` now opens and binds the session the way `pi -p` does, emits `session_shutdown` before disposing, and a headless test drives the real path with no model and asserts the contract is bound, the profile's tool surface is set and the ledger is written before the first prompt.
- Binding the session exposed the next gap: the `implement`, `research`, `bookkeeper` and `auditor` profiles did not grant `report_result`, so a bound unit could never close either. Every profile a contracted unit type runs under now grants it, `regulator check` refuses a contracted unit type whose profile does not (the contract extension also puts the tool on the surface when a contract loads, as a backstop), and the effect declarations distinguish a control-plane record (a report, a proposal, intelligence, a fact: the domain untouched, the record reversible) from a domain write, so a read-only profile can still report.

### Changed
- `regulator check` refuses a committed eval report under `evals/reports/` that still carries the placeholder interpretation `regulator eval` writes without `--interpretation` (by "nobody yet", or "not yet interpreted by a person" in the text). The placeholder is exported from the protocol as `UNINTERPRETED_BY`, `UNINTERPRETED_MARKER` and `isUninterpreted`.
