# Changelog

All notable changes to `@metacoding.io/regulator` are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions follow
[Semantic Versioning](https://semver.org/). Until 1.0.0, a minor version may change the
CLI or the definition's file formats; a patch version does not.

## [Unreleased]

### Added
- Definition versions (#53): a migration note per release and `regulator upgrade` for instances. The manifest records `definition.packageVersion` beside the harness revision and an `upgrades[]` history — each entry from and to (version and revision), the SHA-256 of the committed report under `evals/reports/` whose fingerprint names the target revision or `none`, who and when; both fields optional, so a manifest written under 0.1.3 still validates at schema version 1. The changelog carries a `### Migration` section per version in a typed shape (`MigrationNoteSchema`: one bullet per definition change with its class, its path, the gate it passed — `check`, `scripted` or `live` by report fingerprint, or `none` — and its text), parsed by core's `parseChangelog` and refused by name where a bullet does not fit. `regulator upgrade [--by <who>] [--check] [--definition <dir>]` plans under `planUpgrade` (manifest, installed version, parsed notes, what the instance lacks): it refuses a definition that fails its check, a dirty base, an instance ahead of the package and a version between the two without a note; applies a closed list of idempotent steps, each reported — seed a harness-owned file the instance lacks and never one that exists, the `.regulator/` ignore line — prints the notes of every version crossed under a heading each, records the report fingerprint it was checked against (read, never computed; `none` with a warning when no report ran at the revision), rewrites the manifest and commits on the base branch citing from and to by the person `--by` names, checked against the interaction policy as S5; `--check` prints the plan and changes nothing, and a second run says there is nothing to do. `init` records the package version. `doctor` reports the manifest's package version and upgrade history and says "run `regulator upgrade`" when the installed package is newer; it upgrades nothing. The `instance-manifest`, `doctor`, `identity-promotion` and `advice-decision` cards say what is now mechanical; DEBT row 39 is paid and row 44 narrowed. The first migration note covers everything since 0.1.3 (below), and 0.1.3 carries the retroactive floor a manifest without a version is read as.
- Figures as fragments (#147). `lifecycleFragment()` returns the unit lifecycle as a `<g id="unit-lifecycle" data-viewbox="0 0 800 480">` with its own `<defs>` under prefixed ids and the ids it owns; `renderLifecycleFigure()` is the fragment wrapped in `<svg>`, so the control room is unchanged. Ids come from the definition (a node's is its status, an edge's the pair it joins) and a test holds them identical across renders, unique and drawn only from `UNIT_TRANSITIONS`. Every node and edge is a hotspot (`class="gl fig-hot"`, `data-label`, `data-def`, `data-href`) whose card is built from the row's trigger, step, `automatic` and description, so the docs' and the website's popovers open on a generated figure and a card cannot say what the table does not. `regulator docs --write` now also files every figure in `FIGURES` under `figures/<name>.svg` with absolute docs links, and `docs --check` reports a stale one; the definition check treats `figures/` as derived output beside `dist/`. The docs site copies the figures into `docs/generated/figures/` with site-relative links and the control-room guide embeds the lifecycle; the website copies the file in place of its hand-drawn six states.
- The accept-path split, slice 2 (#138): the prediction record, its resolution from the stores, and the typed `harness-edit` payload. An intelligence signal may carry a `prediction` block — the metric it stakes (built-in or declared), a baseline (a committed report's arm, by the SHA-256 of the report's file), a direction and a size, a `probability` in [0, 1] beside the three-valued `confidence`, and `horizons[]`, each `probe` (a report by fingerprint and an arm) or `live` (the next N units of named types) with the grader value that counts against it. A signal without the block is unchanged and routes as it did; a block missing a part, a probability outside [0, 1] or an unknown metric is refused by the schema. `prediction-resolution` is a new line of the regulatory log, three-valued: at a unit's close or abort the loop reads the named metric with the eval harness's graders over the stores (never the unit's report), compares it with the baseline and the disconfirming value, and appends one reading per unit; a probe horizon resolves once from the committed report it names, against the arm's interval. Disconfirmed is read first; confirmed needs the baseline moved by the magnitude; everything else is inconclusive, which counts against the prediction's precision and never for the edit. A disconfirmed live horizon is a proposal from S3 to S5 to revert or re-decide the advice, routed under the routing policy into an obligation with the prediction's id in its subject; no file is reverted. `HarnessEditSchema` types a proposal's `requestedChange` as a diagnosis (references to evidence records and signals with the unit, attempt, revision and trajectory moment), a change (the diff against one advice file, by profile) and the prediction's id; a payload that claims the kind and lacks a part is refused by the schema, a plain proposal is unaffected. `advice accept` reads a `harness-edit` against the stores first (`checkHarnessEdit`: every diagnosis reference resolves, the prediction carries the block, the profile is declared), takes the target from the payload (`--file`, if given, must agree), cites the prediction's id in the disposition, and the live horizon is open from that decision, read from the obligation; a plain proposal is decided as before. `regulator status` lists every prediction with its horizons, what bet on it, each reading and a precision that counts inconclusive against. The record is `prediction-resolution` (50 records, 48 active); `BOUNDARY.md`'s advice row names the payload. The probe rule and the probe arm are slice 3, after #46; nothing produces a prediction yet.
- Open metrics (#129): a workload declares a metric with its grader, and the fifteen trajectory and outcome counts become the built-in set. `MetricDeclaration` (protocol) is a namespaced name (`workload:<name>/<metric>`, or `instrument:<id>/<metric>` once that record kind exists), a kind (`count`, `rate`, `score`), a direction (`lower`, `higher`, `none`), an optional instrument ref and a `grader.argv`; `workload/<name>.json` carries them under `metrics[]`, beside the workload that owns them. A suite pre-registers a declared name as it does a built-in one and may mark one declared metric `optimise`, the one an optimiser could select on; everything else is reported only, and nothing optimises anything. `regulator check` refuses a suite naming a metric no workload declares, a workload naming a metric it does not own or twice, a grader whose command names no file under the definition, a second optimisation target or a built-in as one, and a judged metric (an instrument ref) until the instrument record carries its held-out score — which no record does yet. `runSuite` runs each declared grader after every unit, in the instance, reading `{ metric, value, observation? }` per line and refusing a grader that fails, measures what it was not declared for or emits nothing for what it was; the values are summarized and lifted exactly as the built-ins, and the report's fingerprint carries each grader's command and file hash. The workload each task's contract names is the one the loop runs, and `regulator eval` takes `--policy`, `--writable` and `--protected` so a suite over another fixture runs under its own layout. The first declared metric is the portfolio's `workload:portfolio/turnover` (`workload/portfolio/turnover.mjs` over `lib/portfolio.js`'s new `turnover`), pre-registered by `evals/portfolio-turnover.json` over the close's first two units under the `manager` and `careless` behaviours; its report is asserted in `src/portfolio.test.ts` and not committed, since nobody has interpreted it. The committed drift reports regenerate byte-identical from their own runs, and a test says so.
- The `portfolio` workload, Phase 1 (#120, under #61): a third workload with nothing new in the control plane. `fixture-portfolio/` is a portfolio under management as plain files — the custodian's exports and the person's fills protected, a tax-lot ledger, targets, trade lists — with six deterministic checks in `test/portfolio.test.js` as its own arithmetic: a feasible target, a trade list that moves toward the target and not past it and lands inside the band, sells from held lots, no wash sale against the lot history, lots reconciled to the fills and the custodian, and a report whose return is the time-weighted one. `workload/portfolio.json` declares five unit types; `profiles/manager.json` has no shell and writes under `lots/`, `targets/`, `trades/pending/` and `reports/`, with `advice/manager.md`; `policies/portfolio.json` budgets them; `contracts/portfolio/` is the September close, with consent on the trade list as one question naming every trade, its lots and its tax. `src/portfolio.test.ts` drives the close scripted under two behaviours: the `manager` closes on host-run evidence, and the `careless` is refused by the three named checks at the first attempt that writes and closes on repair, with the protected prefixes byte for byte what the fixture shipped after both. `regulator fixture <dest> --portfolio` copies the fixture; `docs/examples/portfolio.md` is the worked example and `docs/guide/authoring-a-workload.md` the guide #61 asks for. Phase 2 (#121 to #124) and Phase 3 (#125) wait on this.
- The unit lifecycle is a closed table, and the control room steps through it. `UNIT_TRANSITIONS` (protocol) declares the twelve transitions the S3 loop takes between the six unit statuses, with the loop step that takes each and whether the loop takes it on its own or after a decision outside it; `ExecutionStore.setStatus` refuses a change that is not a row of it, so a status written around the loop (a hand edit, a fixture) fails by name. `unitTrajectory` (core) folds a unit's records — attempts, verdicts, recovery decisions, obligations — through the table in time order and gives each step its why as the records state it: the rule the router applied, the reasons the verdict carries, the obligation the unit waited on and who answered; the fold says when it and the record disagree. `regulator status --json` carries the trajectory per unit. The control room's new *Lifecycle* view draws the figure from the table (`renderLifecycleFigure`, the first of the figures generated from the definition), places the instance's units on it, and steps through the selected unit's trajectory — the transition lights up, the panel says why, `#unit=<i>/<id>@<step>` deep-links a step, a replay row clicked jumps to it, and *copy as a question for your agent* takes the step and its records to the clipboard; the page still asks and writes nothing. The record is `unit-lifecycle` (49 records, 47 active).
- The accept-path split, slice 1 (#110). A profile's advice is a file set seeded like identity: `advice/<profile>.md` in the definition, `regulator/advice/<profile>.md` in the instance, seeded by `init`, rendered by the profiles extension from the instance's copy and cut at the budget policy's new `advice.maxChars` (4000 by default) with the identity's cut-and-warn behaviour; `advice[]` on the profile schema is optional for one release and `regulator check` refuses a profile with both. `DEFINITION_WRITERS` in `protocol` declares the three accept paths (identity, advice, the declaration), the write gate, the bash watch and the closeout derive their protected set from it, `checkDefinition` refuses a definition directory in no class, and `BOUNDARY.md` renders it as "Who writes the definition". `regulator advice accept | reject | promote` mirror the identity commands with one rule more: `--file` must be the advice file the proposal's subject names. Three new records (`advice-decision`, `advice-context`, `definition-writers`); `identity-promotion`, `identity-write-gate`, `identity-untouched-check` and `definition-check` carry both file sets. The rendered profile section is byte-identical before and after the move, and the committed eval reports are unchanged.
- The behavioral canary (`reg.audit.behavioral-canary.v1`; 45 records, 43 active). The budget policy may declare `identity.canary`: a marker every reply must begin with (`{unit}` stands for the unit id, so the marker is the instance's and not one a model has seen) and the number of consecutive replies without it that count. The identity extension renders the rule as a prompt section of its own, outside the identity's character limit, and reads every assistant reply for the marker; a run of misses is recorded as an advisory `audit-finding` (`context-degradation`) from S3* to S3, and the session's status line says how long the silence is. It is an absence canary, the warrant canary's shape: a small rule kept on every reply, whose disappearance says the model has stopped keeping small rules before it drops large ones. It decides nothing: the shipped routing policy notes the finding as trace, and a fresh session stays a person's call (DEBT row 42). The shipped `default` policy declares `[{unit}]` with two misses; `personal-finance` declares none. `BehavioralCanary`, `canaryMarker` and `renderCanarySection` are in core.

### Added
- The identity's context budget is measured, and the cut is reported (#51, DEBT row 25). `renderIdentitySection` truncates at 6000 characters; nothing said when it did. `identityContextBudget` (core) now measures the whole rendering against the limit and names the files cut; `regulator check` and `regulator doctor` warn with the size, the limit and the files — a warning, not a problem, since a long set is valid — and `doctor --json` carries it on the `identity` check (`warning`) with a `warnings` count on the report; the session's status line says `truncated at 6000 of N characters`, and the identity extension records one advisory `operational-signal` per session on the unit, with the files cut as evidence, so the unit's record shows it ran with part of its identity unseen. ### Changed
- The post-merge check is replaced by a pre-merge trial (#48, DEBT row 37). Reintegration now merges the unit's branch in a temporary worktree detached at the base's HEAD, runs the workload's `run_tests` and `run_checks` on that merged tree, and lands a passing tree by fast-forward to the very commit that was verified; a failing tree lands nothing, the base is exactly as it was, and the unit is blocked with the cause `conflict` (repair, under the shipped policy) with the failing checks as its hint. The base is never red; the instance-level obligation the post-merge check opened is no longer produced. `unit finish` runs the same trial with the project's own two checks. The evidence is `pre-merge:*`, bound to the trial commit; a closed outcome carries `preMerge` in place of `postMerge`; a base that moves during the trial is refused as `base-moved`. The `post-merge-check` record is retired as history and `pre-merge-trial` (44 records, 42 active) states the cost, measured.

### Added
- A workload's check entry may carry options, and `glossary-lint` takes one: `{ "name": "glossary-lint", "options": { "commitMessages": "advisory" } }` makes a refused word in a commit message evidence and an `audit-finding` at `advisory` instead of a failed check, while the comment half stays blocking (#47, DEBT row 36). `software-development` and the drift suite's arms declare it; `personal-finance` does not. `regulator check` refuses an option a check does not take. The regenerated sloppy report shows the cost that was being paid: the four units whose only drift was a word in the commit message now close on their first attempt, and the two whose comments drifted are still refused.
- `waitCeilingMs` on the interaction policy (#52, DEBT row 30). A unit paused on a question nobody has answered for that long is routed under the recovery policy's `timeout` cause (retry, retry, escalate by the shipped rules; each routing past the ceiling is one occurrence) and its lease is released, so a unit going nowhere does not hold the worktree. The question stays open with its veto and its history says why; nothing answers on anyone's behalf. The field is optional and the shipped policy leaves it unset: the honest default is to wait.

### Changed
- A registry record's enforcement points are typed (#76). `mechanism.enforcementPoints[]` was free text with the point as a prefix; it is now `{ where, point, note? }` with `where` one of `host` (a session event the Pi host subscribes to, or `dispatcher`), `tool` (a registered tool's execute), `loop` (a step of the S3 loop or the unit lifecycle), `cli` (a `regulator` subcommand) or `check`, and `point` from that place's closed list (`ENFORCEMENT_POINTS` in `@metacoding.io/regulator-protocol`). `regulator check` refuses an unknown place or point by name; tests hold each list against the code, so a host event, a tool, a loop step or a subcommand that is not on its list fails the build. `REGULATORS.md`, `BOUNDARY.md` and the control room print `host:tool_call (write, edit: prepareWritePath)`. This is the first slice of the figures generated from the definition (`ROADMAP.md`, threads).
- A registry record's `introducedIn` is the package version that first shipped it (`0.1.0` for the forty-three records that exist), not the design phase's checkpoint number (`M03`); the schema requires semver and `REGULATORS.md` and the control room render it as "since 0.1.0". ## [0.1.3] — 2026-09-29

The second live drift run (issue #46, on 0.1.2) closed ten of twelve units and found
what happens after the budget guard halts one.

### Fixed
- A halt by the budget guard was failed over as a provider failure. The guard aborts the session when a ceiling is crossed and Pi records the abort as an errored assistant message; the dispatcher read the message alone, opened a fresh session on each declared fallback, and reported "every model in the route failed" when the last one did. Each fallback session also started a new ledger for the same attempt, so the primary's spend and the exhausted marker were overwritten and the loop classed the unit as a dispatch error (recovery cause `environment`) instead of `budget-exhausted`, which the recovery policy routes differently. The dispatcher now reads the attempt's ledger before deciding (`attemptEnd`): a halt is returned to the loop as the attempt's end and is never failed over; only an errored message without a halt is a provider failure. A session that opens on an attempt another session already metered resumes that ledger (`BudgetMeter` `resume`), so the attempt has one ledger whichever sessions ran it, the primary's spend counts against the same ceiling, and a halt stays a halt.
- The default policy's last fallback for every route, `google/gemini-2.5-flash`, is retired by Google for new keys and answered every call with a 404; the routes now fall back to `google/gemini-3.8-flash`, which the pinned Pi registry knows. Nothing checks a route against the provider before dispatch; the `model-router` card says so.
- `regulator unit show … | head` crashed the CLI with `EPIPE` once the reader closed the pipe; the CLI now exits cleanly.

### Migration

The floor the migration notes count from, written retroactively with #53. Nothing an instance carries changed between 0.1.0 and 0.1.3: `init` seeded `regulator/identity/` and added the `.regulator/` ignore line under each, and the identity seed is byte-identical across the four (the policy, profile and registry changes of 0.1.1 to 0.1.3 are read from the definition). A manifest without `definition.packageVersion` was written by one of these four and is read as 0.1.3 by `regulator upgrade`.

## [0.1.2] — 2026-09-28

The first live drift run (issue #46) found the live dispatch path had never been
exercised end to end.

### Fixed
- Live units ran with every session-bound regulator inert. The dispatcher created a Pi session and prompted it, but never called `session.bindExtensions(...)`, which is what emits `session_start` in Pi's own modes. The contract, the profile grant, the budget guard, the identity section and the algedonic path all initialize on that event, so a live unit ran as a plain coding agent: no contract in its prompt, `report_result` refused for want of a contract, nothing metered, every unit blocked as `no-report`. `openUnitSession` now opens and binds the session the way `pi -p` does, emits `session_shutdown` before disposing, and a headless test drives the real path with no model and asserts the contract is bound, the profile's tool surface is set and the ledger is written before the first prompt.
- Binding the session exposed the next gap: the `implement`, `research`, `bookkeeper` and `auditor` profiles did not grant `report_result`, so a bound unit could never close either. Every profile a contracted unit type runs under now grants it, `regulator check` refuses a contracted unit type whose profile does not (the contract extension also puts the tool on the surface when a contract loads, as a backstop), and the effect declarations distinguish a control-plane record (a report, a proposal, intelligence, a fact: the domain untouched, the record reversible) from a domain write, so a read-only profile can still report.

### Changed
- `regulator check` refuses a committed eval report under `evals/reports/` that still carries the placeholder interpretation `regulator eval` writes without `--interpretation` (by "nobody yet", or "not yet interpreted by a person" in the text). The placeholder is exported from the protocol as `UNINTERPRETED_BY`, `UNINTERPRETED_MARKER` and `isUninterpreted`.
